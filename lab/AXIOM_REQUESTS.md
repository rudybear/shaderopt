Every request the shader lab makes of axiom-compute, the guardian's verdict, and the outcome. The lab never edits `~/sources/axiom-compute`; see `AXIOM_SHADER_LAB.md` §2.1.

## Request 001: fragment-shader profile (2026-09-24)

**Request:** `FEATURE_REQUEST.md` at the lab root. **Classification:** LANGUAGE_GAP (execution model, types) + BUILTIN_REQUEST (GLSL.std.450) + ANNOTATION_REQUEST (`@tolerance`, `@rate`, `@range`, `@sink`, `@equiv_fp_tol`) + WORKAROUND (the lab can proceed without any compiler change). **Reviewer:** axiom-guru skill, run against `~/sources/axiom-compute` (read-only), with the gatekeeper protocol at `~/sources/claude-memory/projects/_shared/gatekeeper_protocol.md`.

### Verdict

**Option A endorsed: build the lab's shader IR locally on rspirv `dr::Module`; axiom-compute stays untouched now.** Option B (full shader profile inside axiom-compute) is **REJECTED** under rule 2 (per-project change with one consumer) and the project's own M3.10b falsifiable-value bar. Option C (separate `axc-shader` crate) is **DEFERRED**: it is the right upstream shape if and when a second consumer exists, and Option A is designed so that its crate can move into axiom-compute as `axc-shader` without a rewrite.

Five individual pieces are **welcome upstream on their own** once the lab has proven them (proposals 001-P1 to 001-P5 below, each needing human approval): GLSL.std.450 emitters, a vector scalar type, f16 arithmetic, `@equiv_fp_tol` parsed from source, and the `@tolerance/@rate/@range/@sink` annotation family. A SPIR-V lifter, a Fragment execution model, images/samplers, derivatives, `OpKill` and a generic pass manager are **not** welcome upstream today: no compute consumer exists for any of them.

### Seven-agent analysis

**Agent 1, language analyst.** The driver is GLSL fragment shaders compiled by glslang, not a language gap in `.axc`. The lab never authors `.axc` source; its input is SPIR-V, and its output is SPIR-V. What the lab needs is an IR that (a) is a lossless image of a SPIR-V module, (b) can be edited by typed ops, and (c) can be evaluated on the CPU. Systems that do this today operate on SPIR-V itself (SPIRV-Tools `opt::IRContext` with its pass manager, Mesa's `nir` after `spirv_to_nir`, the MLIR SPIR-V dialect) rather than on a source-level HIR. axiom-compute's HIR is by design a typed tree of the `.axc` surface language (`crates/axc-hir/src/hir.rs`, `expr.rs`); lifting arbitrary SPIR-V into it would mean inventing source syntax for every fragment construct first. That is a fundamental mismatch, not a convenience gap.

**Agent 2, compiler architect.** Where the pieces would go if built: the lifter would be a new crate (nothing in `axc-hir` can receive it); vector types touch `ScalarTy` (`crates/axc-hir/src/ty.rs:16`), the typechecker, `ScalarTypeCache` and every arithmetic emitter in `crates/axc-codegen/src/body.rs`; Fragment stage touches `emit.rs:529,549,1067` (hardcoded `GLCompute`), the interface-variable list, storage classes and the runtime's dispatch (which has no graphics pipeline at all, `crates/axc-runtime`). Reusable today: `get_or_emit_glsl450_set` (`body.rs:233-240`) and the `emit_exp` template (`codegen/src/ext_inst.rs:41-51`) for new ext-insts; `ExtInstBuiltin` (`hir/src/ext_inst.rs:29`) as the registry; `TolerancePolicy` (`driver/src/rewrite_verify.rs:55`) and the closed `Verdict` set (`:158`) as the comparison contract; `axc-optimize`'s deterministic `variant_id` and mixed-radix enumeration (`enumerator.rs:22,68`) as the hole semantics. Complexity of Option B: on the order of FG.6 (`shared[T,N]`, ~5800 LOC across 19 files) several times over, plus a graphics runtime, before the lab's M1 can start. Complexity of Option A for the lab: a lifter is free (rspirv `load_words`), so the cost is the interpreter and the pass framework, which the lab needs in either option.

**Agent 3, SPIR-V backend expert.** Current emission vocabulary is compute-shaped (`buffers.rs:130-155`: `Block`, `Binding`, `DescriptorSet`, `ArrayStride`, `BuiltIn` for invocation IDs; storage classes `Function`, `Input`, `PushConstant`, `StorageBuffer`, `Workgroup`). A fragment profile needs `Output` and `UniformConstant` storage classes, `Location` decorations, `OpTypeImage`/`OpTypeSampledImage`/`OpSampledImage`, `OpImageSampleImplicitLod` (which is only legal in Fragment), `OpDPdx`/`OpDPdy`/`OpFwidth`, `OpKill`/`OpTerminateInvocation`, `OpVectorShuffle`/`OpCompositeExtract`/`OpCompositeConstruct`, `RelaxedPrecision`, `FPFastMathMode`, and ~40 GLSL.std.450 instructions with vector overloads. The lab's probe (`lab/probes/rspirv_roundtrip`) shows rspirv 0.12, the version axiom-compute already pins, loads a glslang fragment module with a sampler, uniform block, loop, helper function and `discard`, and re-assembles it body-identical; only the generator word of the header changes. So the substrate for Option A already exists inside axiom-compute's own dependency set.

**Agent 4, cross-project impact.** Searched every sibling project (`axiom-genome`, `axiom-ports`, `axiom-coder`, `tacit`, `sm120-attn`, `llama.cpp-cohere2moe`, `vulkan/gpugame`) and the shared playbooks. Zero `.axc` files exist outside axiom-compute (57 inside, all in `examples/`). The `axiom-*` name collision is misleading: `axiom-genome`, `axiom-ports` and `axiom-coder` target the separate CPU AXIOM compiler and would not consume a GPU feature. `sm120-attn` has a written but optional intent to use axiom-compute for bf16 coopmat attention (`sm120-attn/docs/ROADMAP.md:79-84`), which is a weak pull for P3 (f16/bf16 arithmetic) and P4 (tolerance from source). `gpugame` compiles Slang to SPIR-V and never mentions AXIOM. The strongest independent pull for vectors and tolerance comes from inside axiom-compute itself: `DESIGN.md:302` defers `subgroup_ballot` "pending uvec4 primitive type" (supports P2), and `ROADMAP.md:337` lists `@equiv_fp_tol`-from-source as a known gap while `AGENTS.md:284-287` documents it as if it existed (supports P4 as a doc/implementation mismatch worth closing on its own merits). No consumer other than the lab exists for a Fragment execution model, images, derivatives or `OpKill`. No proposal here breaks existing `.axc` code: P1 through P5 are additive, and the lab path changes nothing.

**Agent 5, workaround designer (this is the endorsed path).**
1. Create `lab/crates/shader-ir` (Rust, edition 2021) depending on `rspirv = "0.12"`, `spirv = "0.3"` and `spirv-tools = "0.13"`, matching axiom-compute's pins so a later move to `axc-shader` needs no dependency change.
2. IR = `rspirv::dr::Module` plus side tables keyed by result ID (types, def-use, block/loop structure, annotations). Never copy the module into a second IR; edit-ops mutate `dr::Module` in place and re-assemble. The round-trip probe is the M1 gate, kept as a test.
3. Interpreter over `dr::Module` for the fragment profile: f64 reference, f32, and f16-rounding modes; `texelFetch` exact; bilinear/trilinear documented approximations; derivatives over 2x2 quads.
4. Passes as `fn(&mut Module, &Analysis) -> Vec<EditOp>`; every edit-op is a serializable record (op kind, target result IDs, parameters) so `lab/results.jsonl` can replay it. This is the "typed edit-op" the brief specifies.
5. Adopt axiom-compute contracts verbatim: `TolerancePolicy` grammar (`bit-exact | ulp:N | rel:EPS`) extended with the lab's image metrics, the six-value `Verdict` set, the `variant_id = xxh3_64(canonical assignments)` rule, and the "no mocked GPU run" discipline (a CPU-model result is always labeled `predicted`).
6. Annotations (`@rate`, `@range`, `@tolerance`, `@sink`) live in a sidecar TOML next to each shader in `lab/variants/<shader>/`, keyed by source line and SPIR-V result ID, until the upstream proposal 001-P5 lands. They never modify the original GLSL.
7. Lab-side `spirv-val` and `spirv-opt` are the pinned binaries under `~/sources/igl/third-party/deps/src/glslang/build/External/spirv-tools/tools/`, or the in-process `spirv-tools` crate.

**Agent 6, test designer.** For the endorsed lab path: round-trip byte-identity (header excepted) on every corpus shader; interpreter f32 output vs desktop GPU output within a documented tolerance on every scenario; each exact pass proven by CPU f64 equality or a stated ULP bound and by GPU differential; each edit-op serializes and replays to the same SPIR-V hash. For the upstream proposals: see each proposal's test list below.

**Agent 7, quality guardian.** Option B fails three of the guardian's own checks: it serves one project, it contradicts axiom-compute's scope statement (`CLAUDE.md:8`, "NOT a shader/graphics language"), and its complexity dwarfs its benefit to compute users. It also fails the project's M3.10b bar as applied to FG.2: no consumer exists today for a Fragment execution model, images or derivatives inside axiom-compute. Option A costs axiom-compute nothing, keeps the lab merge-compatible by construction, and produces the evidence (which ext-insts, which vector ops, which annotations actually earn their keep) that any later upstream proposal must carry. Simpler alternative considered and rejected: SPIRV-Tools' C++ pass manager as the lab IR. It would give the pass framework for free but no Rust interop with axiom-compute's contracts and no path to `axc-shader`.

### Upstream proposals carved out of this request (each needs human approval; none blocks the lab)

#### 001-P1 GLSL.std.450 emitters beyond `Exp`
- **Category:** builtin. **Area:** HIR (`ext_inst.rs` registry, typecheck), codegen (`ext_inst.rs`). **Complexity:** ~40 LOC per instruction using the `emit_exp` template plus tests; low risk.
- **Specification:** extend `ExtInstBuiltin` with `Sin Cos Tan Pow Log Log2 Exp2 Sqrt InverseSqrt Fma FAbs FMin FMax FClamp FMix Step SmoothStep Floor Ceil Round Trunc Fract Sign` for f32 (and f16 once P3 lands); reserved names added to `RESERVED_EXT_INST_BUILTIN_NAMES`; one `OpExtInstImport` per module via the existing cache.
- **Example:** before, a kernel computes `sqrt(x)` as a Newton loop in source; after, `sqrt(x)` lowers to `OpExtInst %f32 %glsl Sqrt %x`.
- **Tests (min 5):** (1) each instruction emits the correct opcode, asserted with typed `spirv::GLOp` values, never raw u32; (2) exactly one `OpExtInstImport` in a kernel using three different ext-insts; (3) `spirv-val` passes for every instruction; (4) `pow(x, 0)` and `sqrt(-1)`, `log(0)` GPU results compared against a CPU reference with the NaN/Inf outcome documented per instruction; (5) `fma` bit-exact vs `a*b+c` on Lavapipe and within 1 ULP on NVIDIA, recorded honestly; (6) backward compat: all `examples/*.axc` golden SPIR-V unchanged (corpus golden 34/34).
- **Cross-project impact:** shader lab; any compute kernel with activations or normalization.

#### 001-P2 Vector scalar types `vec2/vec3/vec4` of f32 (and f16, i32, u32)
- **Category:** language_gap. **Area:** lexer/parser (type names, `.xyzw` swizzle), HIR (`ScalarTy` or a new `VecTy`), typecheck, codegen (`OpTypeVector`, `OpCompositeConstruct/Extract`, `OpVectorShuffle`, `OpVectorTimesScalar`, `OpDot`). **Complexity:** high, ~3000 LOC; medium risk because every arithmetic emitter gains a vector case.
- **Specification:** explicit types only, no implicit scalar-to-vector broadcast except through an explicit `splat` builtin; component-wise arithmetic; swizzle read and write; `dot`, `length`, `normalize` as ext-insts (depends on P1).
- **Example:** before, `let r: f32 = ...; let g: f32 = ...;` written back through three scalar stores; after, `let c: vec3[f32] = vec3(r, g, b); out[i] = c;` as one `OpStore`.
- **Tests (min 5):** (1) construct/extract round trip bit-exact on GPU; (2) swizzle write to `.zx` leaves `.yw` untouched; (3) mismatched widths rejected at typecheck with a named error; (4) `vec4[f16]` requires `Float16` capability and `StorageBuffer16BitAccess` when stored, preflight-checked like coopmat; (5) `dot(vec3, vec3)` vs CPU within 1 ULP; (6) backward compat: `uvec3` builtin emission for invocation IDs byte-identical.
- **Cross-project impact:** shader lab; compute kernels doing RGB or xyz math; softmax/attention row math could use `vec4` loads.

#### 001-P3 f16 arithmetic
- **Category:** language_gap. **Area:** typecheck, codegen `body.rs:1609` (float literal), arithmetic emitters, capability set. **Complexity:** ~800 LOC; medium risk (denormal and rounding behavior differ per vendor).
- **Specification:** `f16` becomes a first-class arithmetic scalar: literals, `+ - * /`, comparisons, ext-insts from P1; `Float16` capability emitted on first use; explicit `f32_to_f16`/`f16_to_f32` remain the only conversions (no implicit widening).
- **Tests (min 5):** (1) `f16` literal `1.5h` emits `OpConstant %f16 0x3e00`; (2) `a*b+c` in f16 vs the CPU f32-then-round-to-f16 model, with the measured ULP gap on NVIDIA and Lavapipe reported, not hidden; (3) overflow to Inf at 65520; (4) denormal input `2^-24` result reported per device (`shaderDenormFlushToZeroFloat16` is false on the RTX PRO 6000); (5) backward compat: existing `f32_to_f16` storage path byte-identical.
- **Cross-project impact:** shader lab (precision demotion); Q4/Q5/Q6 dequant kernels that already stage `f16` tiles.

#### 001-P4 `@equiv_fp_tol` parsed from source (advisory only)
- **Category:** annotation. **Area:** HIR `lower.rs` whitelist, `axc rewrite-verify` reporting. **Complexity:** ~200 LOC; low risk if the verifier ignores it for the verdict.
- **Specification:** `@equiv_fp_tol(rel=1e-3)` or `(ulp=4)` is parsed and carried on the kernel; `verify_rewrite` reports it alongside the verifier-owned policy but never uses it as the bar (preserves the §4.2 "never read from the thing being judged" rule). Closes the documented gap in `DESIGN.md:1429` and `ROADMAP.md:337`.
- **Tests (min 5):** (1) parses `rel` and `ulp` forms; (2) rejects both at once; (3) rejects negative or zero; (4) verdict unchanged when the source tolerance is looser than the policy (anti-cheat preserved); (5) backward compat: kernels without it unchanged; codegen-inert, golden byte-identical.
- **Cross-project impact:** every rewrite-verify user.

#### 001-P5 Annotation family `@rate`, `@range`, `@tolerance`, `@sink`
- **Category:** annotation. **Area:** HIR whitelist and a new side-table; codegen-inert. **Complexity:** ~400 LOC; low risk.
- **Specification:** `@rate(const|uniform|pixel)` and `@range(lo, hi)` on `let` bindings and params, `@tolerance(...)` on kernels and outputs (same grammar as P4, plus image metrics for the lab), `@sink(address|control|discard)` on bindings. All are carried as data and validated for grammar only; no compiler transformation depends on them in v1. Rationale for accepting: they make optimization intent explicit and machine-checkable, which is the project thesis (`CLAUDE.md:17`).
- **Tests (min 5):** (1) each annotation parses on a `let`; (2) unknown value rejected with `UnknownAnnotationInM0`-style closed error; (3) `@range(hi, lo)` with hi<lo rejected; (4) annotations survive `axc log-opt` source splice; (5) codegen-inert: golden byte-identical with and without; (6) backward compat: all existing examples compile.
- **Revisit trigger, in the FG.2 style:** build v2 (a consumer) when EITHER the lab demonstrates on real devices that `@rate`/`@range` data changes a measured outcome, OR a compute kernel uses `@range` to drive a verified rewrite.

### Outcome
- Lab proceeds on Option A immediately. No axiom-compute change is requested for M1 through M3.
- Proposals 001-P1..P5 are parked until the lab has device evidence for each; P1 and P4 are the cheapest and can be filed first.
- Human approval required for any of P1..P5: **YES**, and each must go through axiom-compute's 7-agent pipeline as a GitHub issue per `ROADMAP.md` "How to contribute".
